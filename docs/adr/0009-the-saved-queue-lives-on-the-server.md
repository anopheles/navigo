# The saved queue lives on the server, and the server wins at startup

Resume keeps the queue, its current entry and position between runs. To make the same queue appear on the laptop and on the main PC, navigo now also stores those three things on the Subsonic server, in the play queue the standard API provides (`savePlayQueue` and `getPlayQueue`, which Navidrome and other OpenSubsonic servers implement). Every write to the local file is also pushed to the server, on the same debounce. The volume and repeat mode are not sent, because two machines have different speakers. The local file stays as the fallback when the server can't be used, and as the home of those per-device settings.

At startup the server's queue wins. navigo asks for it with a 3 s limit and restores it when the server answers with a queue. If the server is unreachable, slow, errors, lacks the calls or holds an empty queue, the local file is used. navigo reads the server's queue once and never again: a running session is not changed by another device, and there is no polling or live channel. The cost of this rule is that edits which never reached the server (made offline, or lost to a failed push) lose to the server's queue at the next start. We accept that, because the alternative is a merge, and a merge of two ordered queues with undo history has no answer a user would expect. Writes to the server are best effort and stay quiet: a failed push is logged, never shown and never marks navigo as offline, since a lost sync of the queue must not interrupt listening. The core stays pure as [ADR 0001](0001-single-writer-core-with-effects-as-data.md) requires. It decides when to load and save, and the effect runner combines the server and the file. `:logout` deletes only the local file, because the other devices still want the server's queue.

We rejected a sync file in the user's own cloud folder (Dropbox, Syncthing and the like). It needs a folder every device shares, conflicts show up as copied files navigo would have to detect, and it asks the user to set up something the music server already offers. We rejected a navigo-specific store, such as a small service or a custom Navidrome endpoint, because it is a second thing to run and secure for one list of IDs, and the queue would then be invisible to the other clients the user may already use with the same account. The server's play queue also keeps the model in [ADR 0002](0002-navigo-owns-the-queue.md): navigo remains the owner of the queue, and the server holds a copy that is only read at startup.
